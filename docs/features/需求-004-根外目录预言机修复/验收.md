## 4. 发现与处置

### 4-1 AC7 口径（对齐既有记录，非本次新问题）

`go build ./...` / `go vet ./...` / `go list ./...` 在本仓库**基线即失败**（`go: updates to go.mod needed`），
肇因是 `memory/notes/`（被剥离出代码仓库的记忆库）内存在导入第三方模块的研究资料 Go 文件
（`github.com/ollama/ollama/...` 等未入 `go.mod`），被 `./...` 扫到。
**基线取证**：`git stash` 掉本次全部改动后 `go build ./...` / `go vet ./...` 同样 `exit=1` → 与本次改动无关。
项目既有记录已把该问题登记为 **P2-5**（`需求-001-记忆阅读页/验收.md:261`：构建门写成 `./...` 本仓库不可执行 →
改为路径限定形式），并写入环境事实（`docs/memory/status.md:41`：「`go build ./...` / `go test ./...` / `go mod tidy`
在本仓库不可用……一律用路径限定形式」）。故 AC7 按 `./pkg/... ./cmd/...`（+ `-tags e2e ./integration/`）判定。

### 4-2 过程事故：行尾（CRLF）

为取得 §4-1 基线而执行的 `git stash pop`，在 `core.autocrlf=true` 下把我改的 4 个文件重新签出为 **CRLF**
（原始字节复检：CRLF=211/319/355/1033，而未改动的 `memory_ops.go` 为 0），导致 `gofmt -l` 报错。
处置：`gofmt -w` 恢复 LF（复检 CRLF=0），并重跑 `pkg/memory`/`pkg/web` 关键用例全绿。
教训：本机 `core.autocrlf=true` 时，**任何 checkout 类操作都会改变工作区行尾**，取证动作也会污染格式门。
该次重写被独立验证者登记为 **P2-1**（过程类，见 §3.5）——正因如此，「验的版本」与「提交的版本」需一次哈希复核（已执行，见 §3.1）。

同类情况在第二轮复核中**再次出现**（**D4**）：第二位验证者进场时 `git status` 无 `docs/features/台账.md`，
数分钟后同一命令列出它（`LastWriteTime = 2026-10-14 11:15:29`）——系作者在验证进行中更新台账状态所致。
未损害可归因性（4 个代码文件在三次采样中哈希一致），但两条合起来给出明确纪律：
**验证窗口内不写工作区**；确需写入时，须先哈希锁定并声明验证范围（两轮验证均做到了）。
