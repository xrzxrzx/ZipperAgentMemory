## 2. 现状局限（本需求要解决的）

| # | 局限 | 具体表现 | 根因 |
|---|---|---|---|
| L1 | **跨语言 / 同义表述召回失败** | 搜 `password` 命中不到正文写「密码」的文件；「兄长」命中不到「哥哥」 | 无词表扩展，纯字面匹配（F1/F2） |
| L2 | **单字切分导致精确率低、噪音大** | 搜「生日」会命中所有含「生」或「日」的文件 | 每字独立成 token，无相邻约束（F1） |
| L3 | **相关性排序不可控** | 关键词出现在路径/标签里的文件，与仅在正文顺带提及的文件**排序无差别** | 所有 FTS 列等权（F4） |
| L4 | **结果不可解释** | 拿到结果只能凭 snippet 猜哪条最相关 | 不返回分数（F6） |
| L5 | **片段过短** | 24 token 常看不出上下文 | `snippet(...,24)`（F5） |

## 5. 顺带取证：敏感文件当前在索引内

`password-vault.csv` / `servers.csv` 属 `.csv`，落在 `indexableExts` 内（F7），因此**内容已进入 FTS5 索引**。实测在索引库字节中直接命中其路径：

```
HIT  structured/password-vault.csv  (offset=5814)
HIT  structured/servers.csv         (offset=5776)
```

影响：`memory_search` 会把密码/凭据**片段**作为命中结果返回，进入调用方（Agent）上下文。

> **处置决定：本需求不做处理。** 用户在 2026-10-18 讨论中明确选择「⑤ 不做」（出于自身使用便利）。
> 该风险为**知情接受**，与决策 8「全库可读（风险知情接受）」同一性质。留痕于此，后续若改变决定另开需求。

## 6. 备选方案评估：向量 / embedding（结论：不采用）

用户曾提出「换向量库」的设想。经评估**本需求不采用**，理由按权重排序：

| # | 理由 | 说明 |
|---|---|---|
| 1 | **与设计基线正面冲突** | `design.md:64` / `README.md:250` 明确排除向量库与 embedding；引入需改权威设计文档并重新获批，属架构变更而非检索优化 |
| 2 | **隐私外发面** | 库内含口令库与服务器凭据（§5）；任何外部 embedding API 都会把文档原文送出库外 |
| 3 | **精确性反向风险** | 个人档案类精确事实（口令、证件、号码、地址）恰恰是字面匹配更强；向量近邻会"看起来相关但事实不同"，且不可判等 |
| 4 | **前期收益低** | 数据量当前为数百 KB～1 MB 级（§3）；数据不足时向量检索价值极低，瓶颈在「没法用」而非「搜不准」 |
| 5 | **落地成本高** | 零 CGO 约束下无成熟纯 Go ANN 方案（`onnxruntime` 需 CGO、`sqlite-vec` 为 C 扩展）；embedding 来源必有一端破红线 |

**保留的正确形态**（若未来重启该方向）：向量应作为 `raw` 层的**可选增强后端**，与 bm25 混合（RRF 融合），默认关闭、敏感分区 fail-closed 排除；且应先解决画像/分层与聚合视图问题，而非直接换检索内核。当前需求-005 的四项改进是通往该方向的前置基础（尤其 L2 的精确率问题，向量并不能替代解决）。

## 7. 本需求的取证结论

- L1–L5 均为**代码级可定位**的局限，且都能用**不引入新依赖**的方式改进；
- 其中 L2（单字切分）需改变**索引内容**，因此必须处理「索引版本 → 重建」问题，并可能触及 `design.md` 对切分方式的记载（C6）；
- 规模与资源约束（C5）在四项改进后仍然满足（索引体积约 2×，仍在磁盘与内存红线内）。
