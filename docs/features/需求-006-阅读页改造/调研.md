## 2. 关键分析

### 2.1 CSRF 风险（用户已选「软删除不二次输口令」）

- Cookie 为 **SameSite=Lax**（F4）。Lax 语义：**跨站发起的 POST / PUT / DELETE 一律不携带该 Cookie**，
  只有顶级导航的 GET 才携带。
- 因此只要**写接口强制 POST**（不接受 GET），跨站 CSRF **无法借用户 Cookie 生效**。
- 结论：用户的决定（不二次输口令）**技术成立**，前提是三条硬约束：
  1. 写接口**只接受 POST**，GET 一律 405；
  2. 保持 `SameSite=Lax`（不得放宽为 `None`）；
  3. 纵深防御：校验 `Origin` / `Referer` 与本站一致（拒绝缺失或跨站），避免将来有人误改 Cookie 策略后静默失去保护。
- 另需注意：Bearer 头不会被浏览器自动附带，故此路径无 CSRF 面。

### 2.2 回收站放哪里

- 若放 `_trash/`（下划线前缀）：**会被索引**（`ShouldIndex` 只跳过 `.` 前缀，F8），回收站内容会出现在检索结果里 → 不合适。
- 若放 `.trash/`（点前缀）：
  - **自动不进索引**（F8）✅
  - **自动不进通用目录树/不可下载**（F9）✅
  - 代价：需**专用 API** 读取（不能复用 `/api/tree`），这正好符合「回收站单独区域」的需求。
- 结论：`.trash/` 是唯一同时满足"不污染检索"与"不污染正常视图"的位置。

### 2.3 删除能力的落点

`pkg/memory` 无删除/移动能力（F6），且 F7 要求一切文件访问必经沙箱。因此必须**在 `pkg/memory` 内新增**：

- 移动到回收站（软删除）：需保留原相对路径信息以便恢复；
- 从回收站恢复；
- 物理删除（清除）。

**不得**在 `pkg/web` 直接 `os.Rename` / `os.Remove`——那会重演需求-004 修掉的越界问题。

### 2.4 与 git autocommit 的关系

服务端若开启 `-git-autocommit`，删除/恢复都会被提交进 `memory/` 仓库历史 → **天然多一层可恢复性**。
但回收站里的文件也会占用仓库体积，需要有清理策略（是否自动过期 = 需求问题，见 `需求.md` §4）。

## 3. 风险

| # | 风险 | 说明 |

| R1 | **安全模型变更** | 从"只读"变为"有限写"。一旦上线，公网可访问的页面具备删除能力（虽仅软删）。须改 `design.md` 并重新获批 |
