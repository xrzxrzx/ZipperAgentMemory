# 需求-008 共享资源库 · 可行性调研（S0）

> 状态：调研完成，待用户定方向
> 起因：用户设想「记忆库存储 AI 可获取的共享资源（头像、安装包等二进制大文件），资源与记忆库都迁到内网服务器，公网访问地址不变（改 nginx）」。
> 定级预估：**T2**（新增外部契约 + 数据模型 + 部署架构变更）

## 1. 结论速览

| 分项 | 结论 | 关键依据 |
|---|---|---|
| **① 记忆库存二进制资源** | ✅ **可行，但需新增能力**（当前接口层完全不具备） | MCP 只有文本收发；`memory_read` 会 `string(data)` 直接吐二进制 |
| **② AI 自动获取资源** | ✅ 可行，**但形态必须是「元数据走 MCP、字节走 HTTP」** | 大文件走 MCP 通道会撑爆 JSON-RPC 消息 |
| **③ 记忆库整体迁内网** | ⚠️ **有条件可行**：文本体验降级可接受，**但大文件外网分发不可行** | 内网出口 **60 KB/s**；100MB = **28 分钟** |
| **④ 访问地址不变（改 nginx）** | ✅ 技术可行 | frpc → frps(公网) → nginx 反代；已有成熟隧道 |
| **⑤ 资源存内网盘** | ✅ 磁盘富余 | 内网 D 盘空闲 **645 GB**；公网机仅剩 24 GB |

**一句话**：**存资源、迁文本记忆库都能做，但"大文件从内网发往公网"这条路基本死**——60 KB/s 的上行决定性不可用。

## 2. 现状能力边界（代码级证据）

| # | 事实 | 证据 |
|---|---|---|
| F1 | `memory_read` 返回 **`textResult(string(data))`** —— 直接把文件字节当字符串返回 | `pkg/mcp/tools.go:217-221` |
| F2 | `memory_write` 只接受 **`Content string`**，二进制需 base64（体积 **+33%**） | `pkg/mcp/tools.go:224-241` |
| F3 | 两个工具**都没有大小上限**，也无 MIME/二进制判定 | 同上（无 MaxBytes 常量） |
| F4 | 存储层 `memory.Store` 可读写**沙箱内任意文件**（不做文本假设） | `pkg/memory/memory_write.go`、`memory_store.go:163` |
| F5 | 索引只收文本扩展名（`.md/.csv/.txt/.json/.yaml/.yml/.toml`），**图片/安装包不进索引** | `pkg/index/rebuild.go:17-27` |
| F6 | 阅读页可**下载**任意文件（`/api/raw`），但**无上传接口** | `pkg/web/handlers.go`（无 upload/write 路由） |

| F8 | `.trash/` 已证明「点目录 + 专用接口」这套隔离模式可复用 | 需求-006 |

## 3. 基础设施实测

### 3.1 两台机器对比

| 项 | 内网 `ZIPPER-WIN-SERV`（192.168.7.104） | 公网阿里云（8.141.89.50） |
|---|---|---|
| 机型 | Dell PowerEdge T130（塔式） | 阿里云 ECS |
| 系统 | Windows Server 2016 | Alibaba Cloud Linux 3 |
| CPU | Xeon E3-1225 v5（4C4T） | 2 vCPU |
| 内存 | **8 GB** | **1.8 GiB** |
| 磁盘空闲 | **C: 292 GB / D: 645 GB** | **24 GB**（40G 盘，已用 14G） |
| **公网出口** | **≈ 60 KB/s（0.48 Mbps）** ← 决定性瓶颈 | 正常 |
| 内网带宽 | 千兆 | — |
| 冗余 | **无 RAID、无虚拟化 → 不能打快照** | 云盘可快照 |
| 现有负载 | DSH Desktop / frpc / Gitea / ARTEX / LdsLite | 记忆库 + 多项公司测试服务 + MySQL + nginx + frps |
| 可用性 | 家用宽带 + 单机；断电/重启需人工核对自启项 | 云主机，SLA 较好 |

### 3.2 带宽实测数据（来自设备档）

| 链路 | 实测速率 | 100 MB 传输耗时 |
|---|---|---|
| 内网 ↔ 内网 | 千兆 | ≈ 1 秒 |
| 公网 ← 内网（经 frp） | **60 KB/s** | **≈ 28.4 分钟** |
| 公网 ← 内网（经阿里云中继 `104 ← 8.141.89.50`） | 409 KB/s | ≈ 4.2 分钟 |

### 3.3 部署通道现状

- nginx：`location /memory/` → `proxy_pass http://127.0.0.1:8932`（本机）
- frps：`bindPort 7000`，`allowPorts` = `3389 / 5985 / 27000-27300 / 10000`
- 内网已有 frpc，且已注册 **100+ 代理**（27000–27099 全占）
- ⚠️ **frps 0.71.0 没有 `reload`**，改配置必须 `restart` → 触发全部代理重注册，约 1 分钟稳定期

## 4. 关键测算：迁内网后到底慢多少

| 场景 | 数据量 | 60 KB/s 下耗时 | 判断 |
|---|---|---|---|
| 阅读页首屏（html+css+js ≈ 18 KB） | 18 KB | **0.3 s** | ✅ 可接受 |
| 打开一篇 30 KB 的 Markdown | 30 KB | **0.5 s** | ✅ 可接受 |
| MCP 检索（返回几十条片段） | 2–10 KB | **0.1 s** | ✅ 可接受 |
| 下载 1 张头像（1.2 MB） | 1.2 MB | **20 s** | ⚠️ 勉强 |
| 下载 1 个安装包（100 MB） | 100 MB | **28 分钟** | ❌ **不可用** |
| 内网 AI 取同一安装包 | 100 MB | **≈ 1 秒** | ✅ 极好 |

**结论**：60 KB/s 对**文本型记忆库**影响有限（亚秒级），对**大文件外网分发**是灾难。
⇒ 「记忆库迁内网」与「资源放内网」两件事的可行性**不同**，不能捆绑判断。

## 5. 三种架构方案

### 方案 A（推荐）记忆库不动，只增「资源区」

- 记忆库（文本）**留在阿里云** → 现有公网体验零变化；
- 内网 `D:\ZipperResources\` 作资源区，内网 AI 千兆直取；
- 资源**清单与元数据**（名称/大小/sha256/MIME/用途/标签）写成 Markdown 放记忆库 → 进索引、可被 AI 检索；
- 公网需要下载时：经 frp 映射一个只读资源端口（60 KB/s，慢但能用）或**暂不支持**。

优点：改动最小、公网体验不降、无迁移风险、可用性不下降。
缺点：**架构分裂**（文本在云、资源在内网），公网取大文件仍慢。

### 方案 B（用户原设想）全迁内网

- 内网跑记忆库 + 资源 + nginx 反代链路；
- 公网经 frp → 阿里云 nginx → 内网（地址不变）。

优点：数据全部自持、内网 AI 体验极佳、磁盘充裕。
缺点：**公网大文件不可用（28 分钟/100MB）**；可用性从"云"降到"家用单机 + 无 RAID"；断电/重启需人工恢复；frps 改配置有 1 分钟抖动。

### 方案 C 记忆库留云 + 资源上对象存储（OSS/CDN）

- 资源放阿里云 OSS（或 Cloudflare R2），公网走 CDN 加速。
缺点：要花钱、数据离家、与"自持"初衷相反。

## 6. 资源区的技术设计要点（无论选哪个方案都需要）

1. **两层分离**（关键）：
   ```
   memory/assets/index.md       ← 清单 + 元数据（Markdown，进索引，AI 可搜）
   <资源根>/avatars/*.png       ← 字节本体（不进索引，只提供下载）
   ```
2. **新增 MCP 能力**（建议）：
   - `memory_assets(query?, tag?)` → 返回清单条目（名称 / 路径 / 大小 / sha256 / MIME / 用途 / 下载 URL）
   - **绝不通过 MCP 传字节**：工具结果只给 URL，字节由客户端自行 HTTP 取
3. **上传通道**：CLI（`zam asset put`）或阅读页表单；两者都要绕过/调整 nginx 的 1 MB 限制（`client_max_body_size`）
4. **完整性**：落盘时算 sha256 写进清单，AI 取用后可自校验
5. **访问控制**：资源区若暴露给公网，必须与阅读页同样口令鉴权，且**只读**
6. **不进索引**：资源目录用**点前缀**或加入 `ShouldIndex` 排除（复用 `.trash` 的模式），避免二进制污染检索

## 7. 风险清单

| # | 风险 | 影响面 |
|---|---|---|
| R1 | 内网上行 60 KB/s | 公网取大文件不可用 |
| R2 | 内网单机、无 RAID、无快照 | 磁盘损坏 = 记忆库与资源**双损**（记忆库目前是唯一真源） |
| R3 | 家用宽带 + 塔式机 | 断电/重启后需人工核对自启项（已有 3+ 项） |
| R4 | frps 改配置需 restart | 100+ 代理重注册，约 1 分钟抖动，可能波及公司测试服务 |
| R5 | nginx `client_max_body_size 1m` | 不调整则任何 >1MB 的上传都 413 |
| R6 | 迁移期间数据一致性 | 记忆库有 git autocommit，但资源区无版本管理 |
| R7 | 公网暴露资源区 | 若不鉴权，等于把安装包/头像公开 |

## 8. 待用户决策

1. **AI 主要从哪里访问记忆库？**（内网为主 / 公网为主 / both）
   - 若"内网为主" → 方案 B 更顺；若"公网（外出设备）为主" → 方案 B 会毁掉阅读页的初衷。
2. **大文件是否需要公网可取？**
   - 只是内网 AI 用 → 方案 A 足够；必须公网也能下 → 只能走方案 C 或接受 28 分钟。
3. **是否接受"记忆库与资源分离部署"？**（方案 A）还是坚持"全部自持在一台内网机"？（方案 B）
4. **资源区是否需要版本/去重？**（如多次上传同一安装包）
