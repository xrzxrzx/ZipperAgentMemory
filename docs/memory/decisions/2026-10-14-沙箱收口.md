# 决策记录：文件系统访问收口 `memory.Store` 沙箱（2026-10-14）

> 依据：外部渗透测试报告 Finding #63（低危·根外目录存在性预言机）＋ 作者本地活体复现；用户选定方案 B（沙箱收口）
> 关联：`docs/features/需求-004-根外目录预言机修复/`（调研/需求/技术方案/实施方案/验收）；提交 `b0e9d04` / `e4a031a` / `3b1df3f`

## 背景

1. **缺陷**：`/memory/api/file` 与 `/memory/api/raw` 在 `store.Read` 失败后会调用 `pathIsDir`，而后者自建
   `filepath.Join(s.store.Root(), rel)` + `os.Stat`，**绕过** `memory.Store` 的 `resolve` 沙箱。`Join` 会先 `Clean`，
   于是 `../../..` 被真正 Stat 到根外：「根外存在目录」返回 `path is a directory (use the tree API)`，
   「根外不存在 / 是文件」返回 `invalid path` → 构成**任意路径处的目录存在性预言机**（1 bit/请求，需有效口令，无速率限制）。
2. **引入与漏测**：该缺陷由 `53ac71e` 引入，而其提交正文与代码注释**都自称**「在沙箱校验之后判定，避免探测口」——
   意图与实现相反；旧用例只断言状态码 400，而两条分支**同为 400**，属结构性漏测。
3. **取证**：两位独立验证者分别活体复现——同一探测在「修复前二进制」上可区分（`0B824866…`/51 字节），
   在「修复后」上逐字节一致（`B73068CA…`/25 字节）。

## 决策

| # | 决策 | 内容 |
|---|---|---|
| 1 | **收口方式** | 元数据查询**下沉** `pkg/memory`：新增 `IsDir` / `ModTime`（先 `resolve` 再 `Stat`）；`pkg/web` 不再直接访问文件系统。用户选定 B（结构性收口），否决 A（仅在非沙箱错误时调用 `pathIsDir`——只是挪判据，web 层仍可裸 `Stat`，同类问题会复发） |
| 2 | **API 形态** | 窄接口（`bool` / `time.Time`），**不**把 `os.FileInfo` 暴露进包 API（与 `List` 返回自有 `Entry` 一致；JEV 0.85）；**不**让 `Read` 兼报 `ErrIsDirectory`（会改动 `Read` 对外契约，连带影响 `zam read` 与 MCP `memory_read` 的错误输出） |
| 3 | **范围** | 只收口 `pkg/web`；`pkg/mcp/server.go:74`（`indexFile`）同类写法**本次不动**（调用点仅在写成功路径，当前不可触发；JEV 0.92）→ 登记为后续需求 |
| 4 | **判定口径** | 验收判据是「越界响应与『根外不存在』**逐字节相同**」，而非「状态码相同」——后者正是旧用例漏掉该缺陷的原因 |
| 5 | **规范固化** | `docs/standards/go-编码规范.md` §5.6：文件系统访问（含元数据查询）必须先经 `memory.Store` 沙箱；禁止自行 `filepath.Join(store.Root(), rel)` 后再访问 |
| 6 | **构建门口径** | 一律用路径限定形式（`go build/test ./pkg/... ./cmd/...`）——`./...` 在本仓库**基线即失败**（`memory/notes/` 内被 gitignore 的未跟踪研究资料导入 go.mod 外的模块），既有记录 P2-5 |

## 理由

- 「一切文件系统访问必经沙箱」本来就是 `design.md` §11.5 与编码规范 §5.1 的既有声明，本次只是把它**变成事实**；
- 预言机不需要内容读取就能透露宿主目录结构，是**持口令视角下的侦察面**；修掉它同时消除「根内 junction → 根外」这条旧实现的第二通道；
- 判定用「逐字节相同」而非状态码，是为了让**回归用例真的能抓住该缺陷**（红/绿双向闭环已验证：新用例在修复前必定失败）。

## 后果

**得到**：根外目录存在性预言机关闭（两轮独立验证、跨验证者全长哈希互证）；阅读页不再有任何对请求输入路径的直接文件系统访问；
不变量写入编码规范；回归用例先红后绿、可长期防复发。

**付出与残余风险**：

| 项 | 说明 |
|---|---|
| 越界文案变化 | `path is a directory (use the tree API)` → `invalid path`（状态码不变；`design.md` §11.4 只约束状态码） |
| `indexFile` 潜伏 | `pkg/mcp/server.go:74` 仍有裸 `Join(store.Root(), rel)` + `os.ReadFile`/`os.Stat`；当前不可触发，需先出现 `Write/Append` 回归才可利用 |
| 平台覆盖 | **仅 Windows 实测**（Linux 上 `/etc` 是绝对路径 → 直接 400，两平台都安全但行为不同）；nginx 反代层未验 |
| 性能 | 每请求多一次 `resolve`（组件级 `Lstat`）——阅读页极低 QPS，无感 |
| **线上未部署** | 本次只提交到本地；**线上仍为修复前版本**，预言机在生产仍在（需有效口令才可利用）。部署属 `zipper-ops`，须用户明确批准 |

## 教训（写进流程记忆）

1. **注释声称安全 ≠ 实现安全**：`53ac71e` 的注释与提交正文都写了「沙箱之后判定」，实现却落在 `Read` 失败分支的**前面**。
   评审安全相关注释时，必须核对**调用点位置**，不能只读注释。
2. **只断状态码的测试是假保护**：两条分支同为 400 时，用例永远绿。安全类断言要落到**可区分的响应内容**上。
3. **验证窗口内不写工作区**：作者为取证跑 `git stash pop`（`core.autocrlf=true` → 4 个文件被重写为 CRLF）导致第一位验证者报 P2-1；
   随后又在验证中更新 `台账.md` 触发 D4。两轮验证均靠**哈希锁定**保住了可归因性——这个动作应成为默认纪律。
