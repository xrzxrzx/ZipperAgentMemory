# 决策记录：检索质量优化（2026-10-18）

> 依据：用户提出「换向量库」设想 → 代码级取证与评估后改为四项低依赖改进；用户批准 S1/S2，并指示「继续直到全部完成」
> 关联：`docs/features/需求-005-检索质量优化/`（调研/需求/技术方案/实施方案/验收）；提交 `44cbb3a` / `c54e3c2` / `5658f96`

## 背景

1. **用户诉求**：现有记忆库检索「纯靠字符串匹配，数据量大了之后有局限」，考虑改用向量库，并希望把大量个人信息纳入。
2. **取证结论**：现状并非纯字符串匹配——是 FTS5 + CJK **单字切分** + AND/OR + bm25 排序（`pkg/index`）。
   真实短板是**精确率与语义召回**，不是性能：当前库数百 KB~1MB 级，查询为毫秒级，性能拐点远未到达。
3. **向量方案评估：不采用**（详见 `调研.md §6`）：与 `design.md §3.3`「明确避免向量库/embedding」基线正面冲突；
   隐私外发面（库内含口令与服务器凭据）；精确事实场景存在反向风险（向量"相关但事实不同"且不可判等）；
   前期数据量不足导致收益低；零 CGO 约束下无成熟纯 Go ANN 方案，embedding 来源必破一端红线。
4. **顺带发现**：`structured/password-vault.csv`、`servers.csv` 属 `.csv`、在 `indexableExts` 内，
   **内容已被索引进 FTS**，`memory_search` 会回显密码片段。用户明确选择「不做排除」（风险知情接受）。
   ⚠️ **实施期间实际踩坑一次**：验证命令把 4 条站点密码 + 1 台服务器 root 密码回显到终端与本次会话上下文
   （未进 git、未外发网络）。教训：**任何针对真库的检索都应先假设输出含敏感内容**；验证一律用临时库。

## 决策

| # | 决策 | 内容 |
|---|---|---|
| 1 | **不引入向量** | 基线冲突 + 隐私 + 精确性 + 收益/成本比不成立；方向改为四项低依赖改进 |
| 2 | **二字组独立成列** | `body_bg` 存相邻二字组、`body` 保留单字；混列会破坏 FTS5 位置语义（短语匹配失效） |
| 3 | **≥2 字 CJK 绝不回落单字** | 否则「生，日」仍被 `"生 日"` 命中，精确率目标不成立——这是本需求的命门 |
| 4 | **查询条件不限定列名** | 实测 `TestFrontMatterIndexed` 暴露：仅出现在 `tags` 的中文（如「部署」）在限定 `body_bg` 时查不到。两类 token 天然不混淆，不限列更简单 |
| 5 | **元数据列单字 + 二字组混写** | 新增 `tokenizeMetaForFTS`，让 tags/created/source 的中文可被 ≥2 字查询命中，同时保留单字匹配 |
| 6 | **索引版本硬保护** | `PRAGMA user_version` + `ErrIndexStale`；空库自动标为当前版本；版本号与索引数据**同事务**写入 |
| 7 | **敏感文件不入索引 = 不做** | 用户明确选择（风险知情接受），与决策 8「全库可读」同性质；留痕于 `调研.md §5` |
| 8 | **拆需求** | 阅读页「软删除→回收站 + UI 美化」拆为 `需求-006`（改安全模型 + 推 `design.md` 决策 8「只读无写接口」，须单独获批） |

## 影响

- **索引内容格式变更**（`indexSchemaVersion = 2`）：旧索引须 `rebuild-index`；`serve` 启动本就全量重建，自动对齐。
- 实测：索引体积 **1.17×**（589,824 → 692,224 字节，远低于预估 2.5–3×）；`serve` RSS **20.3 MB**（红线 60 MB）。
- 对外契约：MCP `memory_search` / CLI `search` 返回加 `(score=x)`；阅读页 `/api/search` 的 `searchHit` 新增 `score`（只增不改）。
- `design.md` 新增 §12「检索实现」；历史章节未改写，并明确 §11.7「无需重建」仅对需求-001 成立。
