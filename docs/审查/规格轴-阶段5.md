## 2. 设计符合度核验（design.md 逐节）

### 2.1 §5 记忆库目录结构（五区）— ✅ 符合

`memory/` 骨架实测：`README.md`、`index.md`、`notes/`（README + 示例 `go-mcp-development.md`，与 design §5 示例同名）、`projects/`（README 说明 `<project>/{README.md, decisions.md, <topic>.md}` 结构）、`structured/`（README + `tasks.csv` 示例，表头=摘要行）、`agent/`（README 说明 `<agent-id>/YYYY-MM.md` 按月归档）、`meta/schema-version`（内容 `1`）。

- 文件约定：蛇形命名、禁止中文文件名、front-matter（tags/created/source）——实现中 ParseFrontMatter 完整支持，front-matter 入 FTS 可检索（TestFrontMatterIndexed）。
- design §5「文件首行（CSV 为表头）作为内容摘要来源」：design 原文为「可自动维护/摘要来源」的非强制机制，实现以 FTS5 snippet 承担摘要功能（阶段 5 验收 D-3 已判定功能等价，无缺失）— 信息级。

### 2.2 §6.1 MCP 6 工具（名称/参数/行为标注）— ✅ 符合

| 工具 | design 规格 | 实现（pkg/mcp/tools.go） | 核验 |
|------|-------------|--------------------------|------|
| `memory_read` | path / readOnly | path 必填，readOnlyAnnotations（ReadOnlyHint=true, OpenWorldHint=false） | ✅ |
| `memory_write` | path, content, overwrite? / destructive, idempotent | overwrite 默认 false 存在即报错；destructiveHint+idempotentHint=true | ✅ |
| `memory_append` | path, content / destructive | 自动 `<!-- appended <RFC3339> -->` 时间戳分隔行；destructiveHint=true, idempotentHint=false | ✅ |
| `memory_search` | query, limit? / readOnly | FTS5 路径+命中片段；limit 默认 20；中文单字切分 | ✅ |
| `memory_list` | path? / readOnly | 缺省=根目录，不递归，目录名带 `/` | ✅ |
| `memory_status` | — / readOnly | 文件数/总大小/最近变更 | ✅ |

- 行为标注 wire 形态实测（阶段 3 验收 e2e 响应片段）：`"annotations":{"destructiveHint":true,"idempotentHint":true,...}` 与 design 表一致。
- tools/list 返回恰 6 个工具，无多余工具（无越界实现）。

### 2.3 §6.2 安全与并发 — ✅ 符合

- 路径沙箱：`resolve` 三层校验（拒绝绝对/带卷名路径 → Clean 后根内判定 → 组件级 Lstat+Readlink 解析符号链接与 junction + 255 层递归上限），返回 `ErrPathOutsideRoot` 哨兵错误（errors.Is 可判）。阶段 1 实测发现并修复的 junction 逃逸（EvalSymlinks 不解析 junction）已在实现与编码规范 §5.2 双重固化。
- 并发写：Store 互斥锁串行化 Write/Append；「同目录临时文件 → fsync → chmod → rename → 目录 fsync」原子写，中途失败只遗留可清理的 `.tmp-*`，不会半写目标。
- 写链路顺序「临时文件 → rename → 索引」：MCP 层 `handleWrite`/`handleAppend` 在 Store 写成功后调用 `indexFile` 同步更新索引，索引失败仅记日志不把写操作回滚为失败（derived state，R7 可恢复）— 与 design §6.2/§9 R7 一致。
- 读不加锁（Read/List 无锁）。

### 2.4 §4.1 MCP 传输双模式（方案 A）— ✅ 符合

- `serve`：常驻单进程合体（watcher + 索引 + MCP），streamable HTTP 挂载 `/mcp`，默认 `127.0.0.1:8931`，`JSONResponse: true`（e2e HTTP 实测握手 + 6 工具通过）。
- `stdio`：按需拉起，启动全量 Rebuild 后 RunStdio，客户端断开退出；不装配 watcher/autocommit（符合「低资源下同时只跑一个实例」）。
- 单一二进制两模式，与 design §4.1 实施说明逐字一致。

### 2.5 §7 迁移双模式 — ✅ 符合

- 目录复制：`scripts/migrate.sh pack`（tar.gz 主路径，缺 tar 回退 zip）+ `restore`（解压 → 重建索引）— 等价覆盖 design 的 `cp -r`。
- git 同步：`bundle`（`git bundle create --all` 单文件，要求 ≥1 提交）+ `restore`（`git clone` → 重建索引）；有远程时用户手动 clone/push/pull（任务书「不做」清单：v1 不自动远程）。
- 迁移后无需合并状态文件：索引是缓存可随时重建（实测 restore 后 rebuild-index 立即可搜）。
