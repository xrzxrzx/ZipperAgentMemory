# 规范轴审查报告（阶段 5）——编码规范符合度

- 审查对象：ZipperAgentMemory 全部 Go 代码（`pkg/memory`、`pkg/index`、`pkg/watch`、`pkg/mcp`、`pkg/git`、`cmd/zam`、`cmd/zipper-agent-memoryd`、`integration/`）
- 审查依据：`docs/standards/go-编码规范.md`（唯一规范依据，逐条对照）
- 审查方式：静态通读 + 针对性 grep（panic / exec.Command / EvalSymlinks / time.Sleep / goroutine / `_ =` 丢弃）
- 范围说明：**只审代码，不审文档**（§9 Git 提交为流程规范，不在代码审查范围）
- 工具链验证：本审查环境未安装 Go 工具链，`go vet ./...`、`go build ./...`、`go test ./...` 无法现场执行（§1.3/§8.3 的"零告警/全绿"声明需在具备 Go 工具链的机器上复核，见"验证项"）

## 一、总体符合度摘要（按规范章节）

| 章节 | 结论 |
|------|------|
| §1 总则 | 符合：每包有 `doc.go`（memory/index/watch/mcp/git），cmd 有包级注释；格式无手调痕迹 |
| §2 命名 | 符合：包名/文件蛇形/导出驼峰/`Err` 前缀哨兵/无拼音中文标识符；无自定义接口（`-er` 规则 N/A） |
| §3 错误处理 | 基本符合：全链路 `%w` 包装、哨兵 + `errors.Is`、无裸 panic 逃逸；少量 `_ =` 丢弃缺注释（见 信息-10/11） |
| §4 并发 | 符合：Store/Index/watcher 均显式锁；goroutine 均有退出路径；fsnotify 去抖合并（滑动窗口） |

| §8 测试 | 符合：关键逻辑（沙箱/原子写/索引/MCP 参数校验）单测齐备、表驱动、`t.TempDir`、无网络；e2e 用 build tag 隔离 |
| §10 资源红线 | 符合：运行期无轮询（生产代码零 `time.Sleep`/Ticker 轮询）、无重量级组件、纯事件驱动 |

## 二、发现清单（按严重度分级）

### 阻塞（必须修）
无。

### 建议（可修可不修，均有依据与理由）

1. **[并发] `pkg/watch/watch.go:96` 与 `:176-181` —— `w.fw` 字段无同步访问**
   - 位置：`Start()` 内 `w.fw = fw`（无锁写）；`Close()` 内读 `w.fw` 并调用 `fw.Close()`（无锁读）。
   - 问题：doc 注释（`:41-42`）明确声明"Close/release 可能从外部 goroutine 调用"，但 `w.fw` 的读写不受 `w.mu` 保护，构成 Go 内存模型下的数据竞争（未定义行为）。
   - 依据：§4.1「共享可变状态一律显式加锁」。
   - 现实影响：当前生产路径（`cmdServe`）从不调用 `Close`，测试亦仅用 ctx 取消，故为潜在缺陷而非已触发缺陷。
   - 建议：`Start` 在持有 `w.mu` 时设置 `w.fw`，`Close` 在 `w.mu` 保护下读取；或将 `fw` 生命周期与 `closed` 通道绑定。

2. **[并发/注释一致性] `pkg/index/index.go:39-41` 与 `:208` —— 注释声称"所有读写经 ix.mu 串行化"，但 `Search` 未取锁**
   - 位置：`Index` 结构体注释（`:39-41`）；`Search`（`:208`）直接 `ix.db.Query`，无 `ix.mu.Lock`。
   - 问题：注释与实现不符；实际安全性来自 `db.SetMaxOpenConns(1)`（`:77`）在连接池层的串行化，而非 `ix.mu`。
   - 依据：§4.1（锁使用）；注释属 §1.2 包级/文档注释准确性要求。
   - 说明：无死锁（Search 不持锁等待连接，Upsert 持连接等待锁，不构成锁序环），行为正确。属文档失实，误导后续维护者（若未来给 Search 加写路径可能漏锁）。
   - 建议：修正注释，或让 `Search` 也走 `ix.mu` 使注释成真。

3. **[错误处理] `pkg/mcp/tools.go:185-200` —— `inputSchema` 内 `panic`（库代码）**
   - 位置：`:198` `panic(fmt.Sprintf("mcp: build input schema: %v", err))`。
   - 问题：§3.4「禁止 panic（除 main 中不可恢复的启动错误）；库代码一律返回 error」字面不符。
   - 权衡说明：输入全为静态字面量，`json.Marshal` 失败仅可能源于编程错误；发生在 `New()` 注册期（等同启动错误）；且所有工具 handler 已有 `withRecovery` 兜底（`:124-133`），不会拖垮运行会话。属**合理权衡**，按任务要求降级为建议。
   - 从严方案：若需完全合规，可改为 `registerTools` 返回 error、`New` 返回 `(*Server, error)`，但当前收益极低。

4. **[并发] `pkg/watch/watch.go:203-206` —— Write 事件逐条同步 `os.Lstat`**
   - 位置：`handleEvent` 的 `Write` 分支。
   - 问题：§4.4「fsnotify 事件必须去抖合并……禁止逐事件同步做 IO」字面不符：每次 Write 事件在事件循环内做一次 `Lstat`。
   - 权衡说明：这是删除竞态守卫（写已不存在的路径不产生事件），单次元数据 stat 开销极小、不读数据；真正的重 IO（读文件内容 + 索引 Upsert）仍在去抖批次内执行。属**合理权衡**，建议级。
   - 替代方案：把 Lstat 推迟到 flush 后由 handler 侧做（`eventToIndex` 读文件时本就处理 NotExist），可彻底消除逐事件 IO。

5. **[代码重复] `pkg/index/index.go:133-160`（Upsert）与 `pkg/index/rebuild.go:118-145`（upsertTx）—— 两段相同 SQL 写入块重复**
   - 位置：两处 `INSERT ... ON CONFLICT` + `SELECT id` + `DELETE docs_fts` + `INSERT docs_fts` 序列完全同构。
   - 问题：Fowler 重复代码（Duplicated Code）——任一表结构变更须同步改两处。
   - 建议：提取共享的 `upsertInTx(tx, path, m, content)`，`Upsert` 与 `Rebuild` 均调用（`Rebuild` 注释已声明为"复用，避免套嵌事务"，说明作者已知悉，但未落地）。

6. **[版本单一来源] `pkg/mcp/server.go:17`（`Version = "v0.4.0"`）与 `cmd/zipper-agent-memoryd/main.go:54`（`version = "v0.4.0"`）—— 双份版本常量靠注释手工同步**
   - 位置：同上。
   - 问题：两处版本号重复维护，注释（`server.go:16`"与进程版本号保持同步"）承认了漂移风险；一旦漏改，MCP 握手版本与进程版本不一致（Divergent Change 前兆）。
   - 建议：单一版本源（如 `cmd` 注入、或抽 `internal/version` 包）。

7. **[命名] `pkg/mcp/server.go:30` —— 结构体字段 `sdk *sdk.Server` 与 import 别名 `sdk` 同名**
   - 位置：`:10` import 别名 `sdk "github.com/modelcontextprotocol/go-sdk/mcp"`；`:30` 字段 `sdk`。
   - 问题：合法但可读性差（`s.sdk` 与包名 `sdk` 视觉混淆），§2 命名精神（完整、无歧义）。
   - 建议：字段改名 `srv` 或 `impl`。

### 信息（记录 / 观察项）

8. **[死状态] `pkg/watch/watch.go:53,170` —— `closed` 通道被 close 但无消费者**
   - `release()` 关闭 `w.closed`，但 `Start` 的 select 从不监听它（退出依赖 `fw.Events/Errors` 通道关闭）。当前是纯标记；可删除，或作为对外同步信号使用。

9. **[静默吞错] `pkg/watch/watch.go:302-306` —— `collectFiles` 读目录失败时 `return nil` 无注释**
   - 属 R7 竞态容错（失败即丢该层事件，Upsert 幂等可恢复），行为可接受；建议补注释说明（§3.1 精神）。

10. **[`_ =` 丢弃] `pkg/watch/watch.go:180` —— `_ = w.fw.Close()` 无注释**
    - §3.1 要求丢弃 error 需注释说明；此为标准 best-effort 关闭（fsnotify Close 幂等），建议补一行注释。

11. **[`_ =` 丢弃] `pkg/memory/memory_write_test.go:49,56` —— `data, _ := os.ReadFile(...)` 无注释**
    - 测试代码；断言前已隐含"上一步成功"前提，但按 §3.1 字面建议补注释或显式检查 err。

12. **[注释精度] `pkg/memory/memory_store.go:26` —— 字段注释"EvalSymlinks 解析后的根目录"表述不精确**
    - `resolvedRoot` 实际由组件级 `resolvePath` 计算（非 `filepath.EvalSymlinks`），注释仅指语义参照。建议改为"组件级解析后的根目录"。

13. **[资源] `pkg/memory/memory_ops.go:46-73` —— `Status()` 每次全树 `WalkDir`，O(n)**
    - `memory_status` 工具可被客户端轮询（`tools.go:90` 描述即如此），大库下每次调用成本随规模线性增长。当前规模（记忆笔记）可接受，§10 资源意识下留意。

14. **[资源] `pkg/memory/memory_write.go:40-73` —— `Append` 每次读入全文件（读改写）**
    - 大文件 append 为 O(n)；与"原子写不产生半行"的取舍一致（§6.1），当前场景合理。

15. **[代码重复] `cmd/zipper-agent-memoryd/main.go:321-348` —— `cmdRebuildIndex` 重实现 `openStoreIndex` 的打开逻辑**
    - `cmdRebuildIndex` 与 `openStoreIndex`（`:112-127`）的 root→store→index 打开序列重复；可复用后者。

16. **[停机竞态] `cmd/zipper-agent-memoryd/main.go:253-269` —— select 先收到 httpErr/watchErr 时，watcher 最终 flush 可能与 `defer ix.Close()` 交错**
    - `ix.Close()`（`:187`）不等待在途查询；若 watcher 背景 goroutine 仍在 flush 批次内 Upsert，会命中已关闭的 db 并记一条日志错误。derived state 可 rebuild 恢复，影响轻微。

17. **[依赖] `go.mod` —— 直接依赖最小化达标，但 MCP SDK 传递引入运行时未用依赖**
    - 直接依赖仅 `fsnotify` / `modelcontextprotocol/go-sdk` / `modernc.org/sqlite`，均上游原版、无 fork（§7.1/§7.3 符合）；`golang.org/x/oauth2`、`google/jsonschema-go`、`google/uuid` 等为 SDK 传递依赖，而 `pkg/mcp/doc.go:20` 声明 v1 不做客户端 OAuth。会增大二进制体积，建议交付验收时实测 §10 红线（常驻内存 < 60MB）。

18. **[验证项] §1.3 / §8.3 无法在本环境复核**
    - 本机无 Go 工具链（`go` 不在 PATH，常见安装位置均未找到），`go vet ./...`、`go build ./...`、`go test ./...` 未执行。代码静态层面未见可预见的 vet/build 告警源，但"零告警/全绿"的正式判定需在具备 Go 1.26 工具链的机器上运行确认（含 `go test -tags e2e ./integration/` 手动验证 §8.3）。

19. **[测试重复] `pkg/memory/memory_path_test.go:72-89,171-185` 与 `pkg/mcp/server_test.go:200-214` —— `createJunction`/`createDirSymlink` 辅助函数三处重复**
    - 建议提为共享测试辅助（如 `internal/testutil`），避免平台分支逻辑漂移。

20. **[测试] 测试中 `mklink` 经 `exec.Command("cmd", "/c", ...)`（§5.4 字面"禁 shell 字符串"）**
    - 仅测试辅助、参数为固定字面量 + `t.TempDir()` 绝对路径、无注入面；生产代码（`pkg/git` 全部调用）严格参数数组。合理，无需改。

21. **[测试] `integration/e2e_mcp_test.go:377-389`（waitReady）与 `pkg/watch/watch_test.go:70-80,113-126`（waitFor/waitWatched）使用轮询 + Sleep**
    - §10 红线针对运行期进程；测试轮询用于消除 Windows fsnotify 时序抖动，属测试惯例，合理。

22. **[覆盖缺口] `pkg/watch/watch.go:238-247` —— 目录删除后不在 fsnotify 层显式 `fw.Remove`，依赖 fsnotify 自动清理失效 watch；「删除目录→同名重建」场景无测试覆盖**
    - `handlePathGone` 只维护 `w.watched` 集合（摘除条目），重建同名目录时 `addTreeLocked` 会重新 `fw.Add`。Windows 上若 fsnotify 未自动摘除旧 watch，`Add` 同名路径的行为需实测确认；`TestWatcherDirRemoveFiresFileEvents` 仅覆盖删除、未覆盖同名重建。建议补同名重建回归测试（建议级倾向，暂列信息）。

## 三、结论

### 阻塞项清单
**无。** 未发现必须修改后才能交付的规范违背项。

### 总体判断
- 代码整体与 `docs/standards/go-编码规范.md` 高度契合：路径沙箱（组件级解析 + junction 防护 + 深度上限）、原子写（临时文件→fsync→rename→索引）、错误链（%w + 哨兵 + errors.Is）、并发模型（显式锁 + goroutine 退出路径 + 去抖合并）、外部命令参数数组、依赖最小化、表驱动测试等规范核心要求**全部落实且有测试佐证**；生产代码无轮询、无裸 panic 逃逸、无 shell 字符串调用。
- 建议项 1-7 均为可修可不修的加固项（其中 1 为潜在数据竞争、2 为注释失实，建议优先处理）；信息项 8-22 为观察/记录。
- **结论：可以进入交付**，条件有二：
  1. 在具备 Go 工具链（≥1.26）的机器上完成 §1.3/§8.3 复核（go vet / go build / go test ./... 全绿，手动跑 `go test -tags e2e ./integration/`），并实测 §10 常驻内存红线；
  2. 建议（非阻塞）优先处理第 1、2 项（并发/注释一致性问题），其余建议可随后续迭代消化。
